## 문제

공공임대주택 당첨자의 약 50%는 실제 입주로 이어지지 않는다. 공고는 자격, 임대료, 면적 같은 정량 정보만 주고 교통, 상권, 공원, 주거 분위기 같은 생활환경 정보는 주지 않아서 신청자가 살고 싶은 동네인지 판단하기 어렵다.

## 접근

팀은 데이터를 하나의 점수로 합치지 않고 네 영역으로 나눴다. 자격과 유형, 주거 물리 조건은 후보를 거르는 데 쓰고, 입지와 교통, 생활환경은 취향 학습에 쓴다.

- 생활환경이 다른 가상 매물 두 개를 비교하는 질문 5개로 8개 생활 취향 축의 가중치를 pairwise logistic 모델로 학습한다. 조건을 직접 물으면 모두 중요하다고 답해 우선순위가 드러나지 않기 때문이다.
- 좌표를 신뢰도 3등급으로 나누고 저신뢰 좌표는 개인화 순위에서 뺀다. 결측은 0으로 채우지 않고 미상으로 둔다.
- 추천 근거는 가까운 역까지의 직선거리와 주변 시설 수처럼 실제 값으로 보여 준다.
- "보증금 3천만원 미만이면서 5년 이내 신축" 같은 문장을 LLM이 조건 필터로 바꾸고, 사용자가 조건 칩과 결과 건수를 확인한 뒤에 지도에 적용한다.

## 판단과<br>트레이드오프

본선 뒤 부산도시공사가 청약센터 개선 설문에 Be:live를 쓰겠다고 요청했다. 단지 데이터와 취향 랭킹은 이미 브라우저에서 계산되고 서버가 필요한 일은 AI 검색의 API 키를 숨기는 것뿐이어서, NestJS와 PostGIS 서버 대신 Cloudflare Pages 정적 배포와 함수 하나로 운영하기로 했다. 무료 플랜이 기관 용도를 허용하고 월 100명 예상 트래픽에도 충분했다.

같은 이유로 로그인과 개인정보 동의 화면을 없앴다. 입력값을 쓰지 않는 로그인과 어디서도 읽지 않는 동의는 공공기관 서비스에서 사실과 다른 고지가 되고, 시민이 청약센터 실계정을 입력하게 만들 수 있다고 봤다.

## 내 역할

팀은 기획, 디자인, 데이터 분석, 개발 네 명이고 나는 개발을 맡았다. 취향 학습 모델과 데이터 품질 규칙은 팀원과 함께 설계했고, 웹 서비스 구현과 배포, 운영은 내가 했다.

- 부산도시공사 CSV를 읽는 유형별 어댑터를 만들었다. 파일마다 다른 인코딩을 자동으로 판별하고 헤더의 단위 표기를 정리해 355단지를 검증 오류 없이 읽었다.
- 팀원의 좌표 복구와 태그 파이프라인을 서비스 코드에 합치고, 좌표 355곳과 정밀 추천군 179곳이 팀원 산출물과 같은지 확인했다.
- 추천 점수를 후보군 안의 min-max 상대점수에서 절대 적합도로 바꿨다. 조건을 바꿔도 같은 취향과 같은 단지면 같은 점수가 나오고, 관심 목록과 상세 화면도 추천 홈과 같은 점수를 보인다.
- 실데이터를 넣은 뒤 드러난 버그를 고쳤다. 취향 랭킹이 생활환경 데이터 없는 후보를 버려 321곳이 39곳으로 줄던 문제와, 준공일 표기가 샘플과 달라 준공연도 필터가 0건이던 문제가 있었다.
- AI 검색은 Gemini 무료 티어에서 JSON 깨짐과 조건 누락을 겪어 Claude Sonnet으로 옮기고, structured outputs로 응답 형식을 강제했다. 모델이 문장 속 지역이나 보증금을 빠뜨리면 원문에서 규칙으로 채우고, Gemini 폴백에는 15초 타임아웃을 걸었다. 2026년 11월 Claude 키가 만료된 뒤에는 코드 수정 없이 Gemini 단독으로 운영하고 있다.
- 발제사 데이터는 커밋하지 않고 합성 데모 데이터를 넣어, 저장소를 공개한 채로 클론 직후 앱이 동작하게 했다.

구현에는 AI 코딩 도구를 활용했다.
